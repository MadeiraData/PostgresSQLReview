CLASSIFICATION RULES for findings:
- If the environment is a managed PostgreSQL service, such as Amazon RDS, Aurora PostgreSQL, Azure Database for PostgreSQL, or Google Cloud SQL, adapt recommendations to managed-service constraints.
  Avoid recommending direct operating system or file-system changes unless the data indicates a self-managed deployment.
- PostgreSQL major version upgrades must always be classified as High effort, regardless of other factors.
- When recommending a PostgreSQL upgrade, recommend upgrading to the latest supported Generally Available (GA) major version appropriate for the environment and validated by application compatibility testing.
  Do not hardcode a version number.
  For managed PostgreSQL services, recommend the latest GA major version supported by the provider and validated by the application compatibility process.
- Any cluster-wide PostgreSQL configuration change, such as shared_buffers, work_mem, effective_cache_size, max_connections, autovacuum settings, checkpoint settings, WAL settings, or parallel query settings, must be classified as Medium risk minimum because it can affect workload behavior across the PostgreSQL cluster.
- Recommendations that require PostgreSQL restart, failover, exclusive locks, major version upgrades, shared_preload_libraries changes, VACUUM FULL, or large index/table rebuilds should mention that a maintenance window or controlled rollout may be required.
- If a configuration value differs from both the default and the recommended value, it may have been set intentionally.
  Do not recommend changing it directly -- instead recommend investigating whether there was a deliberate reason for the setting before making any change.
- Do not recommend VACUUM FULL as a default remediation for bloat.
  If bloat is reported, recommend investigating autovacuum behavior, regular VACUUM, REINDEX CONCURRENTLY, pg_repack, or planned maintenance options.
  Mention VACUUM FULL only when a maintenance window and locking impact are acceptable.
- When discussing work_mem, always mention that it is applied per operation and may be used multiple times per query and per session.
  Do not recommend increasing work_mem globally without considering concurrency, temp file usage, and query patterns.
- For unused indexes, do not recommend immediate removal based only on zero scans.
  Recommend validating over a full business cycle, checking constraints, rare reports, maintenance jobs, and the last statistics reset time before dropping indexes.
- If pg_stat_statements is missing or disabled, explain that workload-level query analysis is limited.
  Recommend enabling it in a controlled way, noting that it may require shared_preload_libraries configuration and a PostgreSQL restart depending on the environment.
- Use CONCURRENTLY-aware wording where relevant, such as CREATE INDEX CONCURRENTLY or REINDEX CONCURRENTLY, while still noting operational risk, longer runtime, and resource usage for large objects.

DATABASE SCOPE RULE:
PostgreSQL Review results are collected from the database where the script was executed.
Cluster-level findings apply to the PostgreSQL cluster.
Database-level, schema-level, table-level, index-level, extension-level, and pg_stat_statements findings apply only to CurrentDatabase unless the JSON explicitly states otherwise.

If the SystemIntroduction contains a Databases list, present it as environment context only.
Do not imply that object-level checks were executed against all listed databases.

If multiple application databases exist, mention that the Review should be executed separately against each relevant application database or results should be merged from multiple executions.

INFRASTRUCTURE INFORMATION RULE:
If machine-level details such as CPU, memory, storage, detailed operating system version, virtualization, or cloud instance type are not available in the collected data, do not infer or invent them.

If PostgreSQLFullVersionString or PostgreSQLBuildAndHostString contains platform information, summarize it as "PostgreSQL build/platform string" only.

Collect them separately from the operating system, cloud provider, VM platform, container platform, or monitoring system if required."
