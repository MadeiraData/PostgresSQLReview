Application Is Running in the Default postgres Database
Scope: Database-levelCategory: Configuration REFERENCES: https://www.postgresql.org/docs/current/manage-ag-createdb.html https://www.postgresql.org/docs/current/manage-ag-templatedbs.html https://www.postgresql.org/docs/current/ddl-priv.htmlApplies to: 1 of 1 databases
Value: The only database in scope is the default maintenance database (postgres), and it contains application objects (schemas public and pgboss).
Impact: HighEffort: HighRisk: Medium
What This Means

the application is using the default postgres database instead of a dedicated application database. The postgres database is intended as a maintenance and administrative landing spot, not as a home for application data. WHY THIS MATTERS: (1) Tooling and administration depend on it: psql defaults, monitoring agents, HA and pooling tools, and scripts that run CREATE DATABASE or DROP DATABASE connect to postgres, so application load, locks, or long transactions there interfere with the database you rely on when something goes wrong. (2) Isolation: a database is the hard boundary in PostgreSQL (separate catalogs, extensions, CONNECT privileges, pg_hba.conf rules, and per-database settings), and running the application in postgres removes that boundary between admin and application context. (3) Backup and lifecycle: pg_dump, pg_restore, cloning with CREATE DATABASE ... TEMPLATE, and logical replication work per database, so a dedicated database can be dumped, restored, cloned, or dropped without touching the admin database. (4) Security: postgres is routinely accessed by DBAs, monitoring roles, and superusers, so application schemas live in a database with much broader access than they need, and CONNECT cannot be restricted to the application roles only. (5) Maintenance and monitoring: wraparound age (datfrozenxid), vacuum activity, and pg_stat_database statistics are tracked per database, so application behavior becomes entangled with the admin database and per-workload analysis is harder. (6) Extension hygiene: extensions are installed per database, so application extensions and their upgrades pollute a database that should stay minimal.

Recommendation

Create a dedicated database for the application (for example CREATE DATABASE appdb OWNER app_owner;), use a dedicated owner role plus separate read/write and read-only roles instead of a superuser, and revoke default access (REVOKE ALL ON DATABASE appdb FROM PUBLIC;). Migrate the application schemas from postgres using pg_dump/pg_restore or logical replication during a planned maintenance window, update connection strings, validate, and then keep postgres for administrative use only. Test the migration in a non-production environment first, since it requires an application cutover. On managed platforms where postgres is the only pre-created database, the same recommendation applies: create a separate database for the application.

Scope: Cluster-levelCategory: Configuration
Value: random_page_cost is more than twice seq_page_cost (the traditional spinning-disk assumption). On SSD, flash, or cloud block storage this can bias the planner toward sequential scans instead of index scans.
Impact: MediumEffort: LowRisk: Medium
What This Means

random_page_cost may not be tuned for SSD, flash, or cloud block storage (it is more than twice seq_page_cost). random_page_cost tells the planner how expensive a random page fetch is relative to a sequential one; the default of 4.0 models spinning disks. On SSD/flash/cloud storage random access is close to sequential, so leaving it high can bias the planner toward sequential scans instead of index scans, producing slower plans.

Recommendation

Confirm the underlying storage type first. For SSD/flash/cloud storage a value close to seq_page_cost (commonly ~1.1) is frequently recommended so the planner does not over-penalize index/random access. Adjust and validate representative query plans before and after. This is a cluster-wide, reloadable change (takes effect via pg_reload_conf, no restart) and affects all query planning. If the value was set intentionally for spinning disks, confirm that before changing it.

About This Assessment

This assessment is a PostgreSQL Review covering configuration, maintenance, observability, statistics, and replication signals collected through SQL against nine application databases on one cluster. Object-level checks (tables, indexes, statistics, bloat) apply only to the specific database in which they were collected; cluster-level checks apply to the whole cluster. The Review does not replace a full architectural review, capacity plan, or application code review.

The findings are based on the collected data at the time of execution. Runtime conditions such as blocking, active sessions, temporary file usage, replication lag, and connection pressure change over time and should be correlated with monitoring data where available. Because results are collected per database, the Review should continue to be executed separately against each relevant application database, or results merged from multiple executions, as was done here.
